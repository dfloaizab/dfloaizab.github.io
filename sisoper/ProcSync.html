Unidad 2 · Sincronización, Interbloqueos y Cierre de la Unidad de Procesos

1. El problema: condiciones de carrera

Cuando varios procesos acceden a datos compartidos (memoria compartida, archivos) y el resultado depende del orden de intercalación de sus instrucciones, hay una condición de carrera. Incluso (*cnt)++ no es atómico: son tres pasos (leer, sumar, escribir) y el planificador puede interrumpir entre ellos, perdiendo actualizaciones.

/* carrera.c: SIN sincronización */
int *cnt = mmap(NULL, sizeof(int),
    PROT_READ|PROT_WRITE,
    MAP_SHARED|MAP_ANONYMOUS, -1, 0);
*cnt = 0;
for (int i = 0; i < 2; i++)
    if (fork() == 0) {
        for (int j = 0; j < 1000000; j++)
            (*cnt)++;
        _exit(0);
    }
wait(NULL); wait(NULL);
printf("%d (esperado 2000000)\n", *cnt);
/* CON semáforo en la región compartida */
typedef struct { sem_t m; int cnt; } Shm;
Shm *s = mmap(NULL, sizeof(Shm), PROT_READ|PROT_WRITE,
    MAP_SHARED|MAP_ANONYMOUS, -1, 0);
sem_init(&s->m, 1, 1);  s->cnt = 0;
/* en cada hijo: */
sem_wait(&s->m);
s->cnt++;            /* sección crítica */
sem_post(&s->m);

Compilar gcc -Wall -std=c99 -D_DEFAULT_SOURCE prog.c -o prog -pthread · Ejecute la versión sin sincronizar varias veces: el resultado cambia.

2. Sección crítica y propiedades de una solución

Estructura

entrada();      /* solicitar acceso */
  SECCION CRITICA
salida();       /* liberar */
  seccion restante

La sección crítica es el fragmento de código que accede a un recurso compartido y no debe ser ejecutado por más de un proceso a la vez.

Tres requisitos

  • Exclusión mutua: a lo sumo un proceso dentro de la sección crítica.
  • Progreso: si nadie está dentro, la decisión de quién entra no puede posponerse indefinidamente ni depender de procesos ajenos a la competencia.
  • Espera acotada: un proceso que solicita entrar no espera por siempre (sin inanición).

Además: no suponer nada sobre velocidad relativa ni número de CPU.

3. Mecanismos de sincronización

MecanismoIdeaVentajaCuidado

Semáforo binario / mutex0/1: wait bloquea, post despiertaEl proceso espera dormidoOrden incorrecto → interbloqueo
Semáforo contadorCuenta unidades disponibles de un recursoControla pools y buffers acotadosOlvidar un post bloquea a otros
Monitor / variable de condiciónExclusión mutua implícita + wait/signal sobre condicionesMás estructurado, menos erroresEn C se arma con mutex + cond (unidad 3)

Semáforo (Dijkstra): entero no negativo con dos operaciones atómicas. wait(S) (P): si S>0 decrementa; si no, bloquea. post(S) (V): incrementa y despierta a un bloqueado. POSIX: sem_init/sem_wait/sem_post (sin nombre, pshared=1 entre procesos) y sem_open (con nombre).

Puente a hilos: sem_wait/post con S=1 equivale a pthread_mutex_lock/unlock; la espera por una condición (buffer vacío/lleno) se resuelve con pthread_cond_wait/signal. Lo que aprenda aquí se reutiliza casi sin cambios.

4. Problemas clásicos de sincronización

Productor-Consumidor

Buffer acotado de N posiciones: semáforos vacio=N, lleno=0, mutex=1. El código completo con memoria compartida está en la página de IPC. Regla clave: primero el semáforo de conteo, después el mutex.

Lectores-Escritores

Varios lectores simultáneos; los escritores acceden en exclusiva. Variante con prioridad a lectores (puede causar inanición de escritores):

/* lector */                 /* escritor */
sem_wait(&mutex);            sem_wait(&escritura);
if (++lectores == 1)         ... escribir ...
    sem_wait(&escritura);    sem_post(&escritura);
sem_post(&mutex);
... leer ...
sem_wait(&mutex);
if (--lectores == 0)
    sem_post(&escritura);
sem_post(&mutex);

Filósofos cenando

5 filósofos y 5 tenedores (semáforos). Si todos toman primero el tenedor izquierdo, hay interbloqueo. Soluciones:

  • Permitir máximo 4 a la mesa (semáforo contador).
  • Orden global: tomar siempre primero el tenedor de menor índice.
  • Filósofo asimétrico (uno invierte el orden).
void tomar(int i) {
    int a = i, b = (i + 1) % 5;
    if (a > b) { int t = a; a = b; b = t; }  /* orden global */
    sem_wait(&tenedor[a]);
    sem_wait(&tenedor[b]);
}
void soltar(int i) {
    sem_post(&tenedor[i]);
    sem_post(&tenedor[(i + 1) % 5]);
}

Cada filósofo es un proceso (fork) y los tenedores viven en memoria compartida.

5. Interbloqueos (deadlock) integrados

Condiciones de Coffman (las 4 a la vez)

  1. Exclusión mutua: recursos no compartibles.
  2. Retener y esperar: se tiene un recurso mientras se pide otro.
  3. Sin expropiación: el recurso solo se libera voluntariamente.
  4. Espera circular: P0 espera a P1, ..., Pn espera a P0.

Grafo de asignación: con una instancia por recurso, ciclo = deadlock; con varias instancias, ciclo es necesario pero no suficiente.

  1. P1 necesita 2 ≤ 3 → termina; disponible = 5.
  2. P0 necesita 5 ≤ 5 → termina; disponible = 10.
  3. P2 necesita 7 ≤ 10 → termina; disponible = 12.

Solicitud: P2 pide 1 unidad. Si se concede: disponible = 2; P2 asignado = 3, necesita 6. Solo P1 (2 ≤ 2) puede terminar → disponible = 4; ni P0 (5) ni P2 (6) caben. Estado INSEGURO → se rechaza aunque haya 3 libres.

6. Límites de los procesos: la motivación para los hilos

  • Costo de creación: fork duplica (con copy-on-write) tablas de páginas, descriptores y PCB.
  • Cambio de contexto pesado: cambiar de espacio de direcciones invalida TLB y degrada la caché.
  • Compartir datos es caro: toda IPC exige llamadas al sistema, copias o regiones compartidas explícitas con sincronización manual.
  • Escalabilidad: un servidor con 10 000 clientes no puede ser 10 000 procesos pesados.
La pregunta de la Unidad 3: ¿y si varios flujos de ejecución compartieran por defecto memoria, archivos abiertos y código dentro de un mismo proceso? Esa es la idea del hilo: más rápido de crear y de comunicar, pero con todas las carreras y deadlocks de esta unidad ahora a nivel de variables globales.

7. Proyecto integrador: mini-shell (mishell.c)

Integra generalidades de procesos, planificación, IPC y sincronización. Requisitos:

  1. Prompt, lectura de línea y ejecución con fork + execvp + waitpid; exit y cd como comandos internos.
  2. Pipelines cmd1 | cmd2 | cmd3 con pipe + dup2.
  3. Redirección >, >> y < con open + dup2.
  4. Segundo plano & con manejador de SIGCHLD (sin zombis); SIGINT no mata la shell, solo al proceso en primer plano.
  5. Comando interno sched rr|fcfs|spn que ejecute el simulador de la página de planificación con procesos ingresados por el usuario.
  6. Comando stats que lea desde una región compartida la cantidad de comandos ejecutados, protegida con semáforo.
while (1) {
    printf("mishell> "); fflush(stdout);
    if (!fgets(linea, sizeof linea, stdin)) break;
    int n = tokenizar(linea, args);            /* TODO */
    if (n == 0 || interno(args)) continue;     /* exit, cd, sched, stats */
    pid_t pid = fork();
    if (pid == 0) { execvp(args[0], args); perror("execvp"); _exit(127); }
    if (!segundo_plano) waitpid(pid, NULL, 0);
}

Cinco ideas para llevarse

  1. El proceso es la unidad de aislamiento y de asignación de recursos; el planificador decide quién usa la CPU y cuándo.
  2. La planificación es un compromiso entre justicia, tiempo de respuesta y rendimiento: no existe el algoritmo perfecto.
  3. Aislamiento implica que comunicar cuesta; elegir el mecanismo de IPC adecuado es una decisión de diseño.
  4. Compartir datos sin sincronizar produce errores intermitentes, los más difíciles de depurar.
  5. El interbloqueo se previene con diseño (orden global de adquisición) mucho mejor que se cura en producción.

Autoevaluación (clic para ver la respuesta)

1. ¿Por qué un lector de pipe no recibe EOF si no cierra su copia del extremo de escritura?Porque el kernel solo reporta EOF cuando todos los descriptores de escritura están cerrados, incluida la copia heredada por el lector.
2. ¿Qué diferencia a Round Robin de SRTF?RR reparte la CPU por quantum sin conocer la duración; SRTF expropia al proceso con menor tiempo restante, optimiza la espera pero puede causar inanición de los largos.
3. ¿Por qué no usar printf en un manejador de señal?No es async-signal-safe: puede interrumpir una llamada interna de stdio y corromper su estado. Use write o una bandera sig_atomic_t.
4. ¿Cuándo es mejor memoria compartida que una cola de mensajes?Cuando el volumen o la frecuencia de datos es alto: evita copias del kernel, pero exige sincronización explícita.
5. ¿Qué requisito de la sección crítica incumple una solución que puede dejar esperando a un proceso indefinidamente?La espera acotada (inanición).
6. Un estado inseguro, ¿implica deadlock?No, implica que podría ocurrir; el Banquero rechaza la solicitud por precaución.
7. ¿Cómo evita el orden global de recursos la espera circular?Si todos adquieren en el mismo orden, no puede formarse un ciclo en el grafo de espera.
8. ¿Por qué los hilos son más livianos que los procesos?Comparten espacio de direcciones y recursos del proceso; solo tienen pila, registros y contador de programa propios, así que crear y cambiar de contexto cuesta menos.
