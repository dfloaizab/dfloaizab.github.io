01

Integración de módulos del SO

Los módulos de gestión de memoria, procesos, I/O y sistema de archivos no son capas independientes: se invocan mutuamente en cada operación del sistema. Entenderlos como un sistema integrado es clave para analizar el rendimiento y la seguridad del SO.

Principio de cierre: Ningún módulo del SO puede funcionar de forma aislada. Una sola llamada al sistema —por ejemplo, read(fd, buf, n)— activa el planificador, el traductor de direcciones virtuales, el driver de E/S, y el VFS de manera encadenada y sincronizada.
Ciclo de integración entre módulos — una llamada write() de principio a fin

Las tecnologías de integración más importantes

Linux Kernel (monolítico modular)

El kernel de Linux es monolítico: todos los subsistemas corren en espacio de kernel (Ring 0) y se comunican directamente. No hay overhead de mensajes entre módulos. Sus componentes clave son: mm/ (memoria), kernel/sched/ (CFS), fs/ (VFS + ext4), drivers/ (E/S), y arch/x86/ (traducción de arquitectura).

Llamada típica en el kernel — path de write()C · Linux kernel
// Simplified path: write syscall → VFS → ext4 → page cache
SYSCALL_DEFINE3(write, int, fd, const char __user*, buf, size_t, count) {
    struct fd f = fdget_pos(fd);          // tabla de archivos del proceso
    if (!f.file) return -EBADF;
    ret = vfs_write(f.file, buf, count, &pos);  // VFS dispatch
    // → ext4_file_write_iter() → page cache → writeout (writeback daemon)
    fdput_pos(f);
    return ret;
}

MMU (Memory Management Unit) + TLB

La MMU traduce cada acceso a memoria de dirección virtual a física usando tablas de páginas de 4 niveles en x86-64 (PGD → PUD → PMD → PTE). El TLB (Translation Lookaside Buffer) es un caché de hardware de las traducciones recientes; un miss en TLB obliga a caminar la tabla completa (100+ ciclos vs. ~1 ciclo en hit). La integración clave: cuando el planificador hace context switch, debe realizar un TLB flush (o usar ASID en ARMv8 para evitarlo). ASLR desordena el espacio virtual como protección.

TLB hit (1–5 ciclos)~99%
TLB miss → page walk (100+ ciclos)~1%
Page fault → disco (millones ciclos)raro
Overhead de seguridad:
KPTI (Meltdown mitigation) obliga a flush de TLB en cada entrada al kernel — overhead de 5–30% según la carga. Mitigado con PCIDs (Process-Context Identifiers) en CPUs modernas.

VFS (Virtual File System) — la capa de abstracción universal

El VFS define las operaciones abstractas (open, read, write, mmap) en términos de estructuras de datos genéricas: struct inode, struct dentry, struct file, struct super_block. Cada sistema de archivos concreto (ext4, NTFS vía ntfs3, FAT32, procfs, FUSE) registra sus implementaciones. El page cache es el punto de integración con la gestión de memoria: las páginas de datos de archivos son también páginas de memoria física compartidas entre procesos con mmap.

Punto clave de integración: mmap() conecta el sistema de archivos directamente con la MMU — las páginas del archivo se mapean al espacio virtual del proceso y el page fault handler las carga bajo demanda, sin read() explícito.

CFS (Completely Fair Scheduler) — integración con E/S

El CFS no opera aislado: cuando un proceso hace E/S bloqueante, el driver llama a schedule() que activa al siguiente proceso del árbol rojo-negro. Cuando la IRQ llega, el proceso es reactivado con wake_up_process() y su prioridad puede ser boosteada si es interactivo. Este boost de E/S asegura que procesos interactivos (como una terminal) respondan antes que un compilador en background.

Integración scheduler ↔ driverLinux kernel — simplificado
// En un driver bloqueante:
wait_event_interruptible(queue, condition);   // duerme el proceso
// En la ISR (interrupt handler):
wake_up_interruptible(&queue);  // despierta → CFS re-inserta

DMA (Direct Memory Access) + IRQ — la integración hardware

El DMA conecta drivers, memoria y planificador: el driver configura el DMA (dirección en RAM, tamaño), el proceso se bloquea, el DMA transfiere bytes sin CPU, y al terminar levanta una IRQ que despacha el scheduler. Esta cadena es la razón por la que se puede tener alta throughput de disco manteniendo la CPU disponible para otros procesos.

Coherencia de caché: Los procesadores modernos con caché escriben en caché antes que en RAM. El DMA puede leer datos stale de RAM. Las CPUs con coherencia de bus (MESI protocol) resuelven esto automáticamente; en ARM hay que hacer dma_sync_single_for_device() manualmente.

Tecnologías de seguridad integradas en el SO

ASLR + KASLR: Aleatoriza las direcciones base del heap, stack y kernel en cada boot. Dificulta exploits que requieren conocer direcciones absolutas (buffer overflows, ROP chains).

CFI (Control-Flow Integrity): Restricción en tiempo de compilación/ejecución de qué funciones pueden ser destino de una llamada indirecta. Implementado en el kernel con Clang CFI desde Android 12+.

seccomp-BPF: Filtra qué syscalls puede hacer un proceso. Docker y Chrome lo usan para reducir la superficie de ataque del kernel desde procesos no confiables.

eBPF + LSM hooks: Permite políticas de seguridad programables en el kernel sin módulos. Falco (CNCF) lo usa para detección de anomalías en tiempo real.

02

Otros sistemas operativos actuales

El SO no es sólo Linux. El ecosistema actual abarca desde RTOS de microsegundos hasta sistemas distribuidos. Cada dominio tiene restricciones distintas que moldean su arquitectura.

🐧
Linux
Monolítico modular · GPL v2
  • Kernel tipo monolítico: todos los subsistemas en Ring 0
  • Módulos cargables (.ko) sin recompilar el kernel
  • Planificador: CFS con árbol rojo-negro
  • Memoria: paginación de 4 niveles (x86-64)
  • Usado en servidores, cloud, embedded (Yocto), supercomputadores
  • eBPF permite extensibilidad sin módulos
🤖
Android (AOSP)
Linux kernel + HAL + ART · Apache 2.0
  • Kernel Linux modificado con Binder IPC, Wakelocks, ION allocator
  • HAL (Hardware Abstraction Layer) en user-space: separa kernel de drivers de fabricante
  • Runtime ART (Android Runtime): compilación AOT+JIT de bytecode Dalvik
  • Planificador: EAS (Energy-Aware Scheduler) para clusters big.LITTLE
  • Seguridad: SELinux obligatorio, scudo allocator, seccomp-BPF
  • Memoria: LMK (Low Memory Killer), ION/DMA-BUF para GPU compartida
🍎
iOS / macOS (XNU)
Mach microkernel + BSD · Darwin (partial open source)
  • Kernel XNU: Mach (IPC por mensajes, VM, scheduling) + FreeBSD (POSIX, VFS, networking)
  • Arquitectura híbrida: partes del SO en user-space (servidores Mach), pero la comunicación es muy eficiente (Mach traps optimizados)
  • IPC: Mach ports — base de toda la comunicación XPC/Objective-C
  • Memoria: Jetsam en iOS (no swap, mata procesos por presión)
  • Apple Silicon (M-series): CPU unificada, Metal GPU, Neural Engine — todo integrado en el kernel
🪟
Windows NT
Híbrido (micro + monolítico) · Propietario
  • Kernel NT: HAL + Executive (I/O Manager, Memory Manager, Process Manager) + microkernel
  • Win32 subsystem corre en user-mode — los drivers pueden correr en user-mode (UMDF)
  • Planificador: prioridades fijas (0–31) + boosting dinámico
  • Memoria: secciones + Working Set + VAD trees
  • WSL2: VM Linux completa con kernel real para interoperabilidad
  • Hyper-V integrado: el kernel de Windows corre sobre un hipervizor propio
⏱️
RTOS (FreeRTOS / Zephyr / QNX)
Tiempo real · Sistemas embebidos críticos
  • FreeRTOS: 9KB de huella, planificador por prioridad, sin MMU obligatoria
  • Zephyr (Linux Foundation): RTOS moderno con soporte de múltiples arquitecturas, usado en IoT/Bluetooth
  • QNX: microkernel, certificado para automoción (ISO 26262) y aviación (DO-178C)
  • Planificación: Rate-Monotonic (RMS), Earliest Deadline First (EDF)
  • Sin memoria virtual obligatoria — énfasis en determinismo, no throughput
  • Latencia de interrupción garantizada: <10 μs en hardware dedicado
🌐
ChromeOS / Fuchsia
Linux / Zircon microkernel · Google
  • ChromeOS: Linux kernel + sistema de archivos A/B para actualizaciones atómicas. Root de confianza en hardware (TPM + Verified Boot)
  • Fuchsia: Nuevo kernel Zircon (microkernel), no POSIX. IPC por canales, capacidades (capabilities model), todo driver en user-space
  • Fuchsia usa FIDL (Fuchsia Interface Definition Language) como protocolo IPC
  • Relevante académicamente: aprendizaje sobre diseño moderno de microkernels sin legado POSIX

03

Temas relacionados y avanzados

Virtualización

La virtualización permite ejecutar múltiples sistemas operativos completos sobre un mismo hardware, cada uno con su propio kernel. El componente central es el hipervisor (VMM — Virtual Machine Monitor).

Tipo 1 — Bare-metal (nativo)

El hipervisor corre directamente sobre el hardware. No hay SO host intermedio. Ejemplos: KVM (Linux, el kernel mismo se convierte en hipervisor vía módulo), Xen, VMware ESXi, Hyper-V.

Mecanismos hardware clave: Intel VT-x / AMD-V — instrucciones hardware para capturar operaciones privilegiadas de la VM (intercept de instrucciones sensibles). EPT/NPT (Extended/Nested Page Tables): dos niveles de traducción de paginación en hardware → la MMU traduce GVA→GPA→HPA sin intervención del hipervisor por cada acceso.

Tipo 2 — Hosted (sobre SO)

El hipervisor es un proceso más del SO host. Ejemplos: VirtualBox, QEMU (en modo full emulation), VMware Workstation.

QEMU + KVM es el stack estándar en cloud: QEMU gestiona los dispositivos virtuales (VirtIO para discos/red), KVM usa VT-x para ejecutar el código de guest sin emular la CPU instrucción a instrucción.

Capas en un host KVM (cloud)

Contenedores (Docker / Podman / LXC)

Los contenedores no virtualizan el hardware: comparten el kernel del SO host. Su aislamiento viene de dos mecanismos del kernel Linux:

Namespaces — aislamiento de visibilidad

Cada contenedor tiene su propia vista de recursos del sistema. Linux tiene 8 namespaces: pid (procesos con IDs propios), net (interfaces de red propias), mnt (sistema de archivos propio), uts (hostname), ipc, user (UIDs propios), time, cgroup.

cgroups v2 — aislamiento de recursos

Controla cuánto de cada recurso puede usar el grupo de procesos: CPU (cpu.weight), memoria (memory.max), E/S (io.weight), red. Docker traduce --memory=512m y --cpus=0.5 a configuración de cgroups v2.

eBPF — Programabilidad del kernel

eBPF (extended Berkeley Packet Filter) permite cargar programas bytecode en el kernel Linux de forma segura (verificados formalmente), que se ejecutan en respuesta a eventos del kernel sin necesidad de módulos ni cambios en el código fuente.

Casos de uso

  • Observabilidad: bpftrace, BCC tools — profiling de CPU, latencia de syscalls, análisis de memoria, tracing de aplicaciones sin modificarlas
  • Networking: XDP (eXpress Data Path) — procesa paquetes antes del stack de red, <1μs de latencia. Base de Cilium (networking en Kubernetes)
  • Seguridad: seccomp-BPF (filtros de syscall), Falco (detección de amenazas)
  • Balanceo de carga: Facebook usa eBPF para balanceo de carga L4 a escala de millones de conexiones

Por qué es revolucionario

Antes de eBPF, extender el kernel requería módulos (.ko) que corren en Ring 0 sin verificación — un bug crashea todo el sistema. eBPF verifica el bytecode antes de ejecutarlo (análisis estático de flujo, límite de instrucciones, sin accesos de memoria inválidos) y lo compila JIT a código nativo.

Ejemplo — tracing de latencia con bpftrace
# Latencia de cada syscall read() por proceso
bpftrace -e 'tracepoint:syscalls:sys_enter_read { @[comm] = count(); }'

Unikernels y kernels especializados

Los unikernels llevan la especialización al extremo: un único espacio de direcciones donde la biblioteca del SO y la aplicación se compilan juntas. Sin user-space ni kernel-space separados. Sin context switches. Sin múltiples procesos.

MirageOS / Unikraft / OSv

  • MirageOS: OCaml funcional, genera VMs UKVM ultra ligeras. Un servidor web en <10MB de imagen
  • Unikraft: modular, elige los componentes del "kernel" que necesitas
  • OSv: JVM unikernel para Java/Scala sin JNI overhead

Ventajas: superficie de ataque mínima, boot en <10ms, sin syscall overhead (todo en Ring 0).

Desventajas: sin multi-proceso, sin usuario dinámico, debugging muy difícil.

Comparación de stack

App tradicionallibc → syscall → kernel → hardware
Contenedorapp → libc → kernel compartido → hardware
Unikernelapp + kernel = UN ejecutable → hypervisor → hardware

Los unikernels eliminar el OS boundary completamente: la función read() no hace trap, llama directamente al driver en el mismo espacio de memoria.

WebAssembly (WASM) como plataforma de sandboxing

WASI (WebAssembly System Interface) define cómo los módulos WASM acceden a recursos del SO (archivos, red, tiempo). WASM se perfila como una alternativa portable a contenedores para funciones serverless sin estado.

WASM como "SO virtual"

Runtimes como Wasmtime y WasmEdge implementan WASI y usan capabilities-based security: un módulo WASM no puede acceder a ningún recurso del SO que no se le conceda explícitamente en el launch. Sin syscall directo — el runtime lo media.

Fermyon Spin / Fastly Compute@Edge usan WASM para serverless con cold start de <1ms vs. ~100ms de un contenedor Docker.

04

Hoja de ruta para tu propio kernel

Construir un kernel funcional, aunque sea mínimo, es la mejor forma de consolidar todo lo visto en el curso. No se trata de reinventar Linux — se trata de entender por qué Linux toma las decisiones que toma.

Herramientas mínimas necesarias

Compilador

i686-elf-gcc o x86_64-elf-gcc (cross-compiler). Compila para x86 sin libc ni runtime del SO host. En macOS: brew install i686-elf-gcc. En Linux: build desde fuente o usa el toolchain de OSDev.

Ensamblador

NASM para el código de bajo nivel: multiboot header, GDT, IDT, cambio a modo protegido/long mode. Alternativa: GNU as (GAS) con sintaxis AT&T.

Emulador

QEMU es el emulador ideal. Permite correr tu kernel sin necesidad de hardware real: qemu-system-i386 -kernel mykernel.elf. Con -s -S conectas gdb para debugging de código del kernel.

Bootloader

GRUB 2 con el protocolo Multiboot es el camino más sencillo. Defines un header Multiboot en tu binario y GRUB lo carga en memoria y entrega el control a tu función kernel_main().

Linker script

Un archivo .ld que define la disposición de secciones en memoria: .text desde 0x100000, .data, .bss. Esencial para que GRUB cargue tu kernel en la dirección correcta.

Lenguaje

C + ensamblador para código de inicialización. En el proyecto final, C es suficiente. Evita C++ al inicio (requiere runtime). Rust es una opción moderna: excelente para evitar UB, aunque la curva inicial es mayor.

Etapas de desarrollo — mínimo viable

1

Modo protegido + GDT

Escribe el header Multiboot en NASM, configura la GDT (Global Descriptor Table) con segmentos de código y datos, cambia de modo real a modo protegido (32-bit). Verifica en QEMU con serial output (outb(0x3F8, c)).

Multiboot header — NASM
; kernel_start.asm
section .multiboot_header
    dd 0x1BADB002        ; magic
    dd 0x00              ; flags
    dd -(0x1BADB002)     ; checksum

section .text
    global _start
_start:
    mov esp, stack_top
    call kernel_main     ; salta a C
    hlt
2

Terminal VGA + output básico

El framebuffer VGA en modo texto vive en 0xB8000. Cada celda es 2 bytes: carácter + atributo de color. Implementa kprintf() escribiendo directamente a esa memoria. Así puedes depurar visualmente desde el primer momento.

Terminal VGA mínima — C
volatile uint16_t* vga = (volatile uint16_t*)0xB8000;
void vga_putchar(char c, uint8_t color, int col, int row) {
    vga[row * 80 + col] = (uint16_t)c | ((uint16_t)color << 8);
}
3

IDT + manejadores de interrupción

Configura la IDT (Interrupt Descriptor Table) con 256 entradas. Maneja las excepciones básicas (división por cero, GPF). Configura el PIC 8259 y habilita el timer IRQ0 — el corazón del preemptive scheduling. Sin interrupciones no hay planificador.

Habilitar timer IRQ0 — C
// Remapear PIC para que IRQ0 esté en vector 0x20
outb(0x20, 0x11); outb(0xA0, 0x11);  // inicio init
outb(0x21, 0x20); outb(0xA1, 0x28);  // vector base
outb(0x21, 0x01); outb(0xA1, 0x01);  // modo 8086
outb(0x21, 0xFE);  // habilitar solo IRQ0 (timer)
sti();              // habilitar interrupciones
4

Gestor de memoria física (buddy/bitmap)

Implementa un gestor de frames físicos. La forma más simple es un bitmap: 1 bit por frame de 4KB. Para asignar, busca el primer bit en 0. Implementa pmm_alloc_frame() y pmm_free_frame(). La información de memoria disponible la provee Multiboot en la estructura multiboot_info_t.

5

Paginación (Virtual Memory Manager)

Configura el Page Directory y Page Tables para x86. Mapea el kernel al espacio alto (higher-half kernel, 0xC0000000). Implementa manejo del page fault (ISR 14) para crecer el heap on-demand. Con esto tienes un sistema de memoria virtual básico.

Habilitar paginación — C + ASM inline
// CR3 apunta al Page Directory físico
write_cr3((uint32_t)page_directory);
// Habilitar bit PG en CR0
write_cr0(read_cr0() | 0x80000000);
6

Planificador básico (Round Robin)

Crea una estructura task_t con el PCB mínimo: pila de kernel, puntero de instrucción, estado. En el handler del timer IRQ0 guarda el contexto del proceso actual (empuja registros a la pila) y carga el contexto del siguiente en la cola. Esto es el context switch.

Context switch mínimo — NASM
; Salva contexto del proceso saliente, carga el entrante
switch_context:
    push ebp
    mov  [eax + OFFSET_ESP], esp  ; guarda ESP actual
    mov  esp, [ecx + OFFSET_ESP]  ; carga ESP del nuevo
    pop  ebp
    ret                           ; salta al PC del nuevo

Recomendación para el proyecto final del curso

Para un kernel de grado universitario, el objetivo mínimo recomendable es: boot via GRUB → modo protegido → terminal VGA → IDT + timer IRQ → gestor de frames → paginación básica → Round Robin con 2–3 tareas hardcodeadas. Esto cubre todos los módulos del curso en un sistema funcional.

Para diferenciarse: implementar un heap de kernel con kmalloc/kfree (buddy allocator o slab simple), o agregar el controlador de teclado PS/2 para input interactivo, o implementar un sistema de archivos en RAM (initrd/ramfs).

El lenguaje recomendado es C con GNU extensions. Usa -ffreestanding -nostdlib -O2 -Wall y el linker script para producir un ELF Multiboot. El emulador QEMU con -serial stdio permite debugging por puerto serial desde el primer día.
